# 3種類のリクエストの見分け方

Staff役に連携企画機能を追加すると、利用者からの依頼は性格の異なる3種類に分かれる。これを一つの応答フォーマットへ押し込めようとすると、単独の地図依頼が連携企画の説明で水膨れしたり、逆に連携企画が3段落の定型フォーマットに収まりきらず情報が欠落したりする。最初にこの3種類を見分けることが、連携企画機能を追加する上での土台になる。

出典: [`dwg7/chukei` issue #3](https://github.com/dwg7/chukei/issues/3) のルーティング規則を一般化したもの。

## A. コンテンツ単独依頼

特定の場所・主題について、地図やその他の地理空間コンテンツへのリンクを直接求めている依頼。

例: 「◯◯地区の昔と今の空中写真を見比べたい」「△△川流域の浸水想定区域を見たい」

この場合は、Staff役が本来持っている地図生成規則（User → Map Intent → Cartographerリンク）をそのまま全面適用する。連携企画の説明・選定理由・内部処理過程などを付け加えない。既存の地図単独用の応答フォーマットを変更しない。

## B. 連携企画依頼

学校・自治体・防災機関・業界団体・博物館・研究機関・地域団体などとの連携案、授業案、提案書、説明資料、会議案、ワークショップ、展示、調査計画などを求めている依頼。

例: 「小学校の先生に地域学習の授業を提案したい」「自治体の防災担当者と一緒に試せる企画を考えたい」

この場合は [`process.ja.md`](process.ja.md) の連携企画プロセスに従い、[`output-structure.ja.md`](output-structure.ja.md) の構成で応答する。提案全体をAの3段落フォーマットへ押し込めない。ただし提案の中で個別のコンテンツリンクを作る場合は、そのデプロイメントのCartographer固有規則（実在する識別子だけを使う、URLを正確に構築するなど）は省略せず適用する。

## C. 成果物作成依頼

既に検討した連携方策やコンテンツリンクを使って、文書・スライド・メール・授業案・チェックリスト・説明資料・会議資料などの具体的な成果物を作る依頼。

例: 「この地図リンクを入れた授業案を作って」「これまでの議論を1枚のスライドにして」

この場合は、それまでの会話内容と既に確認済みのリンクを保持し、指定された形式に再構成する。既に確認されたリンクを勝手に短縮・変更・再構築しない。リンクがまだ用意されていない場合は、必要な問いを整理した上で通常のコンテンツ生成規則に従って用意する。

## 判定に迷う場合

A/B/Cの境界があいまいな依頼（例: 「授業で使えそうな地図を教えて」）は、依頼の主語がコンテンツ（A寄り）か、相手の活動全体（B寄り）かで判断する。判断に必要な情報が決定的に欠けている場合だけ、最小限の確認質問をする。多くの場合、利用者の言葉だけから合理的な仮定を置いて初案を出す方が、相手の時間を尊重する([`principles.ja.md`](principles.ja.md) 原則3・4)。
